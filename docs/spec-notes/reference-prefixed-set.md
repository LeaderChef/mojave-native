# Reference-prefixed vanilla Set statements

[observed, owned script data] A TTW source unit spells a vanilla assignment `reference.Set localVariable to expression`. Its compiled statement has the existing reference prefix before the Set opcode, followed by an ordinary local-variable target. Before this change the native reader rejected a prefix on non-call statements and the source compiler treated this spelling as an unknown function. Original source and byte payloads remain private.

[documented] The GECK Calling reference page describes an explicit reference as a function caller, distinct from script-variable ownership: https://geckwiki.com/index.php/Calling_reference . The Ref Variable page spells a remote assignment `Set Reference.variable to value`: https://geckwiki.com/index.php/Ref_Variable . Neither page documents the prefixed Set edge case itself.

[hypothesis] Preserve the prefix as optional statement metadata, separate from the existing target's `VarRef::on`. It supplies the default caller only while evaluating the assignment's expression; an explicitly qualified call still wins. It must not turn a local target into another object's variable or replace an explicit remote target. Restore the previous expression-caller scope on success and failure. Unprefixed Set keeps its current behavior and JSON shape.

[limits] This is an inference from the stored statement shape and documented calling-reference model, not an original-game runtime observation of prefixed Set. In particular, a null prefix with a constant-only expression needs a future original-game observation; retain existing host rules when a function is called on a null reference. Support the observed vanilla Set expression grammar first; extended/compiler-override variants must not silently erase a prefix.

[observed, native checks, 2026-11-07] The five authored source/decode/VM regressions changed from one pass/four failures before the fix to five passes afterward. They cover caller/target separation, explicit caller precedence, scope restoration after an error, legacy JSON and rejection of unsupported prefixes or extended rewrites. The required root release suite passed 2,311 tests with eight ignored; root and engine Clippy and the ARM64 release build passed. The smoke Python suite passed (74 tests, four skipped).

[observed, private owned-data consumer] The original TTW unit now compiles without errors; its stored bytecode and the source-compiled bytecode both decode without Raw statements. Running its actual GameMode block on the equipped armor's item instance writes the local cooldown once, leaves it unchanged at the same game time, then updates it after the cooldown. The fixture explicitly grants power-armor training before equipping; its first run without that prerequisite could not exercise the assignment. No original game or mod files were changed. The consumer is a core game-state check, not a rendered playthrough or an original-engine parity comparison.

[observed, native Metal smoke] The additive `reference-prefixed-set` scenario ran with the 18-plugin owned TTW profile in an isolated windowless M4 Pro/Metal runner. Its authored GN script read Luck through both an explicit caller and a statement-default caller: both returned 5. The run exited normally after four scheduled seconds without GPU validation errors. It did not control the user's app or measure visible gameplay performance. Reproduce with `python tools/smoke run --only reference-prefixed-set` and the documented executable/data environment.

[limits] These results establish the native behavior above, not a complete TTW, Nuclear Sunset, save-format, visual or multiplayer acceptance claim. The statement-caller hypothesis still needs original-engine observation, especially for null or otherwise invalid prefixes. No dependency version checks or warnings were changed.
